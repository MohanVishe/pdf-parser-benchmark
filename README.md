# PDF Parser Benchmark

**A small, scored benchmark harness for PDF text extraction.** Five parsers sit behind one `extract(path) -> str` interface. Four hand-verified documents stress different failure modes: ten scripts including RTL and Indic, a three-column page, a dense ruled table, and a scanned typewritten page. The results tables are generated by the script from `results/results.json`, and CI re-runs the benchmark and fails if any quality metric stops reproducing.

## Why this exists

Every document-AI pipeline starts by picking a parser, and the choice is rarely made on purpose. A parser that scrambles a multi-column page or flattens a table doesn't fail loudly. It returns plausible text, and the retrieval system built on top quietly degrades. This harness makes the failure visible: the same documents go through every parser, and each output is scored against a reference a person checked.

### What the run shows

Each point below is read from the tables above and can be checked in the committed extractions.

- **Right-to-left text: each parser fails differently.** PyPDF returns Arabic and Urdu in correct logical order. PDFPlumber returns both sentences fully reversed, in visual left-to-right order. PDFMiner scatters the words across the page with the letters inside each word reversed; part of the Arabic sentence ends up in the middle of the Urdu block.
- **Hindi and Bengali break in all three.** No parser returns either sentence intact. Conjuncts such as `सुस्त` come out as `सु त`, and PDFPlumber also moves vowel signs (`तजे` for `तेज`). The text layer does carry the conjuncts: PyMuPDF, used here only to draft references, recovers them.
- **PyPDF puts one word per line on the Google-Docs sample** (141 lines, 1.0 words per line). On the Federal Register pages it keeps normal lines, and it has the lowest CER on both.
- **PDFPlumber reads straight across columns.** On the three-column page its BoW-F1 (0.964) shows that nearly every word is there, but CER 0.786 and WER 0.945 show them interleaved line by line across the three columns. PyPDF and PDFMiner follow the columns (CER 0.046 and 0.050).
- **Tables: row grouping and cell integrity trade off.** PDFPlumber keeps all 21 rows on their own lines, but splices the amounts into the middle of the six wrapped descriptions (78/84 cells). PyPDF keeps every cell (84/84) but breaks those same six wrapped rows (15/21). PDFMiner keeps each citation with its description but emits the amounts as a separate block, so no row survives (0/21). On the sample's 4×2 table, only PDFPlumber keeps the rows.
- **The scanned page returns nothing** from all three (PDFMiner emits a single form-feed character), as expected with no text layer. The image-only 18% of the sample (banner and handwriting) is lost the same way.
- **Invisible text leaks through.** All three emit the Federal Register's white typesetting slug (`VerDate …`), which a reader never sees; that is part of why their output runs longer than the reference.

Every extraction is committed under [`results/extractions/`](results/extractions/), so each finding can be checked by opening the files side by side.

## The corpus

| Document | What it stresses | Source | Licence |
|---|---|---|---|
| `multilingual-sample` (2 pp.) | English, Spanish, Hindi, French, Arabic, Bengali, Russian, Portuguese, Urdu and Chinese on one page; emoji including ZWJ sequences; a 4×2 table; page 2 is a website-banner screenshot and a handwriting sample (images only) | Authored for this repo in Google Docs | MIT (this repo) |
| `fr-notice-3col` (1 p.) | Three-column layout, running header, bold/italic run-ins, invisible typesetting slugs | [Federal Register Vol. 91 No. 185, p. 61023](https://www.govinfo.gov/content/pkg/FR-2026-09-25/pdf/2026-19690.pdf) (2026-09-25) | Public domain, U.S. Government work (17 U.S.C. 105) |
| `fr-table` (1 p.) | 21-row ruled table with wrapped cells, dot leaders, a footnote, then three columns of text | [Federal Register Vol. 91 No. 9, p. 1449](https://www.govinfo.gov/content/pkg/FR-2026-01-14/pdf/2026-00535.pdf) (2026-01-14), page 3 of the source PDF | Public domain, U.S. Government work |
| `naca-scan` (1 p.) | A 1922 typewritten page scanned to JPEG, no text layer | [NACA Technical Note No. 112](https://ntrs.nasa.gov/citations/19930080884), H. J. E. Reid, page 2 | Public domain, U.S. Government work (NTRS: public use permitted) |

The three downloaded PDFs are cut to the scoped page with pypdf. For the NACA page, the invisible OCR text that the scanner software had added is removed with `PdfWriter.remove_text()`. The JPEG itself is copied byte for byte, so the page behaves like a raw scan. [`corpus/build_corpus.py`](corpus/build_corpus.py) repeats all of this from the source URLs and checks each download's SHA-256 against [`corpus/manifest.json`](corpus/manifest.json), which also records the page, transform and licence for every document.

## Method

**Reference text.** Each `corpus/*.reference.txt` is a transcription of everything a reader sees on the page, in reading order: each column top to bottom, tables row by row. Text inside content images counts (the banner, the handwriting, the scan). Logos and invisible white text don't. Each reference was drafted from PyMuPDF's text layer (PyMuPDF is not one of the benchmarked parsers) or, for the scan, typed from the image. It was then checked against 150–400 dpi renders region by region. A final pass listed every reference word that no extractor produced, and each one was resolved against the image. That pass also exposed a scorer bug that ate a sentence period before a dot leader, now fixed and tested. The scan's typewritten digits were cross-checked against the NTRS catalogue record, which corrected one misreading (NO. 112, not 113).

**Normalization** (applied to reference and output alike): Unicode NFKC, which folds Arabic presentation forms and ligatures to base letters. Arabic/Farsi yeh and kaf/keheh are folded, because PDF fonts map one shared glyph to either. Variation selectors are dropped, dot leaders removed, and all whitespace collapsed.

**Metrics**, all in [`scoring.py`](scoring.py) with tests in [`tests/test_scoring.py`](tests/test_scoring.py):

| Metric | What it measures | What it misses |
|---|---|---|
| CER / WER | Character / word edit distance to the reference ([jiwer](https://github.com/jitsi/jiwer)). Order-sensitive: a paragraph in the wrong place costs about twice its length. | Can't tell *missing* text from *misplaced* text |
| BoW-F1 | Order-free word overlap | Says nothing about order: read it next to WER |
| Table rows / cells | A row is intact if all its cells come out on one line, in order (for a wrapped cell, the text on the row's own line). A cell is found if its full text appears anywhere. | Header rows are excluded; no column-alignment check |
| RTL order | Each Arabic/Urdu sentence: logical order, fully reversed (visual order), or out of order | Sentence-level only |
| Indic | Whether each Hindi/Bengali sentence survives exactly, plus the share of its words that do | No per-glyph diagnosis |
| Seconds | Median wall-clock time per document over the repeats | One machine; not comparable across machines |

The previous version of this README argued against automated scoring, because a single similarity score rewards the wrong things. That argument still holds for a single score, so this harness never reports one alone. Order-sensitive (WER) and order-free (BoW-F1) scores are read together, and structure (table rows, RTL order, Indic shaping) is checked separately.

### Limitations

- **Four documents, five pages.** That's enough to show *how* each parser fails, but not to rank parsers on your documents. Treat the table as a record of these pages.
- **One transcriber.** The references were checked against renders but never double-keyed.
- **Default settings only.** pypdf's `extraction_mode="layout"`, PDFMiner's `LAParams` and PDFPlumber's tolerances can all change these numbers.
- **Timings come from one Windows machine** and cover text extraction only.

## The five parsers

| Parser | Runs | Reads scans? | Adapter |
|---|---|---|---|
| [PyPDF](https://pypdf.readthedocs.io) | Local | No, text layer only | [`parsers/pypdf_parser.py`](parsers/pypdf_parser.py) |
| [PDFMiner.six](https://pdfminersix.readthedocs.io) | Local | No, text layer only | [`parsers/pdfminer_parser.py`](parsers/pdfminer_parser.py) |
| [PDFPlumber](https://github.com/jsvine/pdfplumber) | Local | No, text layer only | [`parsers/pdfplumber_parser.py`](parsers/pdfplumber_parser.py) |
| [LlamaParse](https://developers.llamaindex.ai/python/cloud/llamaparse/) | Cloud | Yes | [`parsers/llamaparse_parser.py`](parsers/llamaparse_parser.py): the current `llama-cloud` SDK (`client.parsing.parse(..., expand=["text"])`). The older `llama-parse` package is deprecated. |
| [AWS Textract](https://aws.amazon.com/textract/) | Cloud | Yes (OCR) | [`parsers/textract_parser.py`](parsers/textract_parser.py): renders each page to a 200-dpi PNG (PyMuPDF's default of 72 dpi gives OCR a 612×792 image) and calls `DetectDocumentText` |

**Two questions narrow the choice before any benchmark does.** Does the document have a text layer? If not, the three local parsers return nothing, as the `naca-scan` row shows, and you need OCR. Can the document leave your infrastructure? If not, the cloud parsers are out, whatever their accuracy.

## Run it

Requires [uv](https://docs.astral.sh/uv/). Dependencies are pinned in `pyproject.toml` and locked in `uv.lock`.

```bash
git clone https://github.com/MohanVishe/pdf-parser-benchmark.git
cd pdf-parser-benchmark
uv sync                                   # local parsers + scorer
uv run pytest -q                          # scorer, adapters, cloud gating
uv run python run_benchmark.py --local-only --repeats 5
```

The last command rewrites `results/` and the results block above. To check that your machine reproduces the committed quality metrics without overwriting them:

```bash
uv run python run_benchmark.py --local-only --repeats 1 --out /tmp/pdfbench --check results/results.json
```

To include the cloud parsers, install their SDKs and set credentials, then drop `--local-only`. Each cloud parser runs only when its keys are present:

```bash
uv sync --extra cloud
cp .env.example .env    # LLAMA_CLOUD_API_KEY, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY
uv run python run_benchmark.py
```

To try your own PDFs without references (characters and seconds only), point `--input` at a folder: `uv run python run_benchmark.py --input my_pdfs/ --out out/`.

## Layout

```
├── run_benchmark.py        # extract → score → results/results.json, RESULTS.md, README block; --check for CI
├── scoring.py              # normalization, CER/WER, BoW-F1, table, RTL and Indic checks
├── parsers/                # one file per parser, each exposing extract(pdf_path) -> str
├── corpus/                 # PDFs, hand-verified references, manifest.json (source, licence, checks), build_corpus.py
├── results/                # committed: extractions/<doc>/<parser>.txt, results.json, RESULTS.md
└── tests/                  # scorer unit tests, adapter tests on a generated PDF, gating and --check tests
```

Adding a parser means writing one module with `NAME`, `KIND`, `PACKAGE`, `REQUIRES` and `extract()`, then adding it to `PARSER_MODULES` in `run_benchmark.py`.
